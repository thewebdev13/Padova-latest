# Free production health check and paused-project recovery

## Scope and schedule

Production is [Padova on Render](https://padova-production.onrender.com), connected only to Supabase **unugynfzmxjxifgofxjr**. The cloud scheduler is the existing private [production repository's Production health workflow](https://github.com/shmuelp12/padova-production/actions/workflows/production-health.yml). It runs at **06:17, 14:17 and 22:17 UTC daily**, and can be run manually. It works while the Owner's computer is off.

The scheduler requests `GET https://padova-production.onrender.com/api/health`. The uncached endpoint validates production configuration before connecting, then reads the installed adapter marker in `padova.app_schema_versions` with the existing restricted application role. PostgreSQL supplies the check timestamp. A success proves that the hosted application and its production database were reachable together. It reads no customer or financial records and creates no staff session, booking, payment, journal event or other persistent data. QA is rejected before connecting. No new database grant, migration, credential, GitHub secret or backup change is needed.

The public endpoint exposes only availability, the non-secret project reference and database timestamp. Errors return generic HTTP 503 responses without database errors, connection strings, financial information or credentials. Application data still requires individual staff authentication. A separate [Production health watchdog](https://github.com/shmuelp12/padova-production/actions/workflows/production-health-watchdog.yml) runs daily at **18:43 UTC**, checks that the primary workflow is enabled and has succeeded within 26 hours, and fails visibly otherwise. It only reads GitHub workflow metadata, without contacting either database.

The workflow uses a standard Linux runner, an eight-minute maximum, no checkout, third-party action, artifact or cache. Three attempts of up to two minutes accommodate Render Free cold starts. The existing GitHub Free allowance and **account Actions $0 overage budget with usage blocking** were verified on 2 November 2026; keep that cap unchanged. Included-usage alerts are already on. If the allowance is exhausted, checks stop rather than incur a charge. No paid service or plan is added.

## Results and failures

Open the workflow link above. Each run records a timestamped PASS/FAILED summary and retained GitHub logs. HTTP failures, a missing marker, incorrect production identity, stale response, inaccessible scheduler history or a previous completed run more than **26 hours** old fail visibly. The actual database read is attempted even if the history check fails. An initial run establishes the monitoring baseline.

GitHub's existing Actions notification preference is **Email, failed workflows only**, using the account's existing notification email. No notification address or other account preference is changed. The workflow's scheduled actor is the account that created the schedule. To investigate: open the newest red run, read its summary, then use **Run workflow → main → Run workflow** after resolving the cause. A later green run records recovery; prior failures remain visible.

GitHub can delay/drop scheduled jobs; scheduling away from the top of the hour and running three times daily reduces that risk. The separate watchdog detects a disabled primary workflow or a lack of successful runs without waiting for the primary check to recover. The primary history check also flags an interruption when execution resumes. If GitHub itself is completely unavailable, both workflows are disabled, or the free allowance is exhausted, neither can send its own missing-run alert while stopped: **no run in 26 hours is an unhealthy monitoring state**, even if the last run is green. Check the last-run time and GitHub billing/usage alerts. Keep this private repository and both workflows enabled; public repositories have an additional 60-day inactivity disable policy. Free monitoring reduces inactivity risk; it cannot guarantee Supabase will never pause. Supabase's own pause-warning and paused-project emails remain a separate signal.

## Exactly how to resume production if Supabase pauses it

1. Sign in to [the production project dashboard](https://supabase.com/dashboard/project/unugynfzmxjxifgofxjr) with the existing Owner account. Confirm the project reference is **unugynfzmxjxifgofxjr**, named **Padova Travel - US Private Trial**. Do not select QA (`cnpyvmhgbtyleckyirye`).
2. On the paused-project screen, click **Resume project** and confirm. Stay on the Free plan; no upgrade, new project, database reset or migration is required. Wait until Supabase finishes resuming and reports the project available. Its existing data/configuration should return with the same project reference.
3. Open [the production health endpoint](https://padova-production.onrender.com/api/health). Allow the sleeping Render application to wake. Expect HTTP 200 with `status: healthy`, `database: reachable`, `projectRef: unugynfzmxjxifgofxjr` and a current `checkedAt`.
4. Run **Production health → Run workflow → main → Run workflow** in GitHub and verify the database step passes. A resumed scheduler after a long gap may produce one red history check; the next run should pass once the gap has been acknowledged by a completed run.
5. Open Padova, sign in using the usual individual staff account, reload and verify an existing booking is visible. Do not create fake transactions to test recovery. If health still fails, inspect Render service logs and the workflow summary without copying secrets into issues or chat. Recheck production identity and connectivity; do not switch to QA as a fallback.
6. If the **Resume project** action is absent or fails, stop changes and use Supabase support/status information. Current Supabase documentation allows dashboard resumption for **up to one year after pausing**. Beyond the supported window or if data is genuinely unavailable, follow the existing recovery runbook in the Padova project (docs/RECOVERY_RUNBOOK.md) and the Owner’s Recovery Kit, preserve the project/evidence and obtain a reviewed recovery plan. Do not restore the pre-cleanup synthetic archive over daily production bookings.

The encrypted backup, encryption-key custody, off-device archive and independent restore procedure are unchanged. A keepalive is not a backup, and routine pause/resume does not require restoring an archive. Go-forward and historical migration gates are not modified by this health check.
