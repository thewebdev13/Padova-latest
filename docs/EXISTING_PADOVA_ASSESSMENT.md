# Existing Padova schema reuse assessment

Historical assessment before implementation. The Owner subsequently authorized reuse; current adapter code, review-only SQL and remaining activation work are documented in [PADOVA_ADAPTER](PADOVA_ADAPTER.md). Statements below describing the pre-adapter public-schema application refer to that assessment snapshot.

Read-only assessment, 28 October 2026. Sole project: **Padova Travel - US Private Trial**, **`unugynfzmxjxifgofxjr`**, **`us-east-1`**. No migration, schema creation, data write, enrollment, configuration change, restart or rebuild was performed.

## Recommendation

**Prefer extending the existing `padova` schema and adapting the current application to it. Do not create `padova_v1` or install the denied public-schema bundle.** The existing schema has substantial reusable domain structures, but is not compatible with the application unchanged. This is an assessment, not approval to alter the database. Preserve completed interface/business features while adapting storage and identity integration.

## What exists and where it came from

Catalog inspection covered columns, constraints, numeric precision, all Padova function definitions, triggers, views, policies, effective grants, migration history, exact table counts and aggregate evidence provenance. No source transaction/person payloads or passwords were exported. No mutating RPC was called.

Eleven recorded migrations dated 27 October 2026 establish the earlier private schema, posting/review API, owner enrollment, financial hardening, original-source review, asset-return correction, historical contacts, lifecycle/duplicate controls, isolated tests, application export and refund follow-ups. This predates the current repository build. It is evidence of earlier Padova implementation work; metadata inspected here does **not** establish which named AI/Tab session or human authored each object.

### Existing operational schema

`padova` has **35 tables, three views and 15 functions**. Its eight public wrapper RPCs remain present. Core structures cover parties/relationships/corporate rules; bookings/travelers/confirmations/itinerary; charges; customer receipts/allocations; supplier obligations/payments/allocations; assets/movements/sales; funding/reversals; commissions; referral terms/payouts; separate supplier/customer refund cases and settlements; notes/attachments; requests/idempotency; staff/settings; audit/review history.

Exact nonempty tables:

| Table                 | Rows | Meaning                                                                                                                                                                        |
| --------------------- | ---: | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `padova.review_cases` |  947 | 919 migration, 19 key-finding and nine coverage cases; all open.                                                                                                               |
| `padova.audit_events` |  947 | Creation events for those review cases, all at the same import timestamp; actor is NULL on all 947. Preserve this import attribution rather than inventing a logged-in author. |
| `padova.settings`     |    1 | `America/New_York`; operational entry disabled; backup verification timestamp NULL.                                                                                            |

Every other operational table, including bookings, parties, receipts, supplier payments, assets, staff and financial movements, currently has **zero rows**. Thus the large populated dataset is evidence/review material, not a posted production ledger. Empty operational tables still represent useful completed schema work.

All 35 tables have RLS enabled and no RLS policies. `authenticated` has schema usage but SELECT access to zero operational tables. Eight public RPCs grant authenticated execution and deny anonymous execution; their SECURITY DEFINER implementations perform staff checks. Existing triggers supply audit, append-only protection and refund guards. These controls merit reuse after workflow-specific review, not blanket replacement.

### Existing evidence schema

`padova_staging` contains four tables: **two batches, 167 evidence-file records, 37,071 evidence records and zero migration mappings**. Reuse this as the evidence/provenance store, not as automatically verified transactions.

- `handoff_20261027_readonly_v1`: historical snapshots, prior AI allocations and media inventory; explicitly unverified and overlapping, with no financial postings.
- `live_sheets_20261027T195340934Z`: current-sheet snapshots preserving formulas, effective values, notes and links; explicitly no operational postings. There are 4,108 `live_sheet_snapshot` records.
- File groups include 72 table exports, 17 snapshots, 47 supporting files, 23 technical files, two current-sheet files and handoff/manifest/validation documents.
- Evidence classes distinguish Owner statements/confirmations, primary-source claims, proposals, superseded AI records and unresolved material. Examples include 16,144 unresolved records and 1,507 superseded AI system records explicitly marked non-additive to the current ledger. Preserve these classifications; never sum all evidence as transactions.

There are useful historical-directory and historical-booking functions over staging. They return unverified/source records separately from the operational ledger. Do not call them safe for Employees unchanged: historical-booking output includes source sale/cost and raw payloads.

## Comparison with the current application

The application expects **46 tables**; 20 share names with existing tables. Shared names do not establish compatible columns or economics. Its SQL currently targets `public`, and cloud startup checks its own public migration ledger. Pointing it at `padova` would fail and could attach wrong meanings to amounts if adapted superficially. Do not run its current migrations against `padova`.

## Safest connection sequence — proposal only

1. Preserve the same US project, existing UUIDs, evidence classes, review/audit history, operational lock and schema names. Leave both denied public installation and `padova_v1` proposals inactive.
2. Implement a repository storage/provider adapter for existing `padova` tables and Auth identities. Keep UI and permission semantics; use aliases/conversions in the application or new, explicitly reviewed API functions rather than replacing existing tables/views/RPCs.
3. Produce a minimal, object-by-object additive extension list for gaps: granular grants/versioning/security audit, operational metadata/tasks, protected travelers/payment accounts, lot/unit support, correction/settlement details and balanced journal support. Absence of a same-named table is not proof a new one is needed. Never backfill evidence into live financial tables automatically.
4. Validate locally against a faithful **structural** copy with synthetic data and populated preservation fixtures. Run the current financial/auth acceptance scenarios against the adapter, including cents/dollars conversion, FIFO/proportional boundaries, null incomplete profit, reversals, actual Auth actor IDs and denied direct RPC access.
5. Present exact proposed SQL and access changes for Owner review before any database write. Obtain required private credentials without resetting passwords. Begin with a restricted read-only connection; enable writes only after approved schema/security changes, verified independent backup/restore and actual individual-user acceptance.

No new project, duplicate schema, destructive SQL or historical import is required to deliver this assessment. Reuse is feasible at the domain level; safe drop-in runtime compatibility is **not** established. Full concurrency/financial/security validation of the old RPCs has not been performed, and source manifests were inspected as metadata rather than re-checksummed against original files.
