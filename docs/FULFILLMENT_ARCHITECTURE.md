# Incremental fulfillment architecture

The existing US `padova` foundation, original adapter and accounting ledgers remain canonical. **Migration `20261029012515_padova_fulfillment_catalogs_units` is installed in the existing US project**, with marker `20261029_fulfillment_catalogs_units`. Its exact source is preserved in `supabase/migrations/20261029012515_padova_fulfillment_catalogs_units.sql`; `db/padova/fulfillment-object-summary.json` records the immutable checksum and installation status. Do not regenerate or reinstall it. It created no schema/project and changed no staging/evidence/review/history/balance rows.

## Model

- **Programs / instruments:** configurable provider/program name, money/points/count units, core/ancillary/both roles, restrictions and optional expected redemption/rebate terms. Rules are configuration, never proof of a receipt or automatic earnings.
- **Program accounts:** canonical holder, nickname, ownership and at most four reference characters. No account passwords, full card/account numbers or bank credentials.
- **Travel components:** several flights/stays/services can belong to one booking, each retaining provider, channel, purchased-from source, dates and confirmations. Existing booking-level itinerary/funding remains intact.
- **Fulfillment details:** several fulfillments can serve each travel component. Each links to one existing funding component. Provider, source/payee, holder/account, program, instrument and core/ancillary role stay distinct. Outside-source awards create the actual agreed source cost/payable without creating owned points or inheriting the source's internal rebate economics.
- **Inventory profiles / lot-use links:** instruments and accounts attach to existing assets. FIFO lots, movements and basis remain the inventory truth. Exact component-to-movement links prevent multi-lot/multi-asset returns from restoring unrelated funding.
- **Expected events / append-only updates:** requested/pending transfers and rebates do not move inventory or profit. Actual transfer completion consumes owned source lots and creates destination lots carrying original basis plus actual fees; ratios/bonuses are configurable. Actual owned-points rebates restore original consumed basis once. Available rebates may be reversed with dated correcting events. Already-spent value is held for review, never forced negative.

## Money and compatibility

The simple single-product booking UI uses `create_initial_travel` to atomically create its initial travel row and link each initial funding component. The default remains false for existing command compatibility; prior saved bookings are not backfilled. Initial links retain the inventory profile's instrument/account and ancillary role. An ancillary-only instrument does not confirm the base travel cost. Multi-travel entry instead sends `travel_components_input` with explicit funding `travel_index` assignments; the two input modes are mutually exclusive. Provider/source/channel/dates/confirmations stay on their respective travel rows. Parent dates derive from the component envelope; original snapshot, charges, funding and any customer receipt commit together. Deleting a draft component clears funding assignments before another save. No new database objects are required.

Installed travel rows remain immutable. For an initial component created by this single-save path, reads project the latest audited booking revision over its original operational details. Additional components and canceled originals remain independent. Itinerary snapshots preserve original and revised travel. No installed migration or table trigger is rewritten.

Explicit `acquisition_source_status: Unknown` means an outside source exists but is unidentified, independent of blank or Direct Airline. It blocks an assumed provider/payee fallback. Unknown costs remain pending; no generic financial counterparty is invented. Directory and catalog creation can occur inline with parent draft preservation and actual-user permission checks.

Money remains exact integer cents inside the engine and decimal USD at the installed adapter boundary. Nullable unit columns extend assets and funding without backfilling/reinterpreting existing rows. Null retains the installed points-versus-money interpretation. Certificates use whole counts, independent of their acquisition basis. The existing refund discriminator is retained for compatibility; an additional nullable quantity label distinguishes count-based returns without removing an existing constraint.

No second financial ledger is introduced. Customer receipts/allocations, supplier obligations/payments, assets/lots/movements, dated profit movements, journal entries and actual-user audit continue through the existing atomic command engine. Missing or incomplete cost remains unknown. When cost is explicitly pending, provisional recognized profit is deferred through a dated reporting adjustment, preserving prior history.

Every travel component must have confirmed fulfillment cost or an explicitly attributed no-supplier-cost confirmation before overall profit becomes known. The latter creates no fictional funding/payment/face value. Existing recorded funding can be linked once to a travel component without posting it again; a unique funding link prevents accidental reuse across components. Actual dates and reasons remain in the same command/audit history.

## Prepared database change summary

Adds nine narrow tables: `programs`, `instruments`, `program_accounts`, `travel_components`, `inventory_profiles`, `fulfillment_details`, `funding_asset_uses`, `expected_events`, `expected_event_updates`. Adds nullable unit metadata to existing assets/funding/refunds. Updates only the related adapter view projections and write functions to carry units correctly; existing column order and null behavior remain compatible. There is no backfill, unrestricted UPDATE, DELETE, TRUNCATE, DROP or historical posting.

New tables have RLS and explicit server-only SELECT/INSERT access; browser roles receive no access. Configuration and events are append-only in this batch. Existing RPC privileges and installed migration artifacts are unchanged. The application checks extension availability and continues using the installed adapter when it is absent.

The concise pre-application object/change summary was provided. Post-install evidence, review, audit and settings hashes match the preflight exactly; 37,071 evidence rows and 947 reviews remain intact. Browser roles have zero new-table privileges. The existing backup reader has SELECT on all nine new tables, no new write/admin rights and no plaintext Vault access. Further catalog versioning, broader issuer-specific adjustments and the complete 26-case product/browser matrix must be verified before calling the expanded model production-ready.
