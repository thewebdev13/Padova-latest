## Lost laptop or repository

1. On a trusted replacement computer, regain either authorized Google account and retrieve **Padova Recovery Kit**. Regain the Drive account/folder separately. Do not paste keys into chat, email, a command line or a website outside the chosen password manager.
2. Download the desired dated `.enc` archive, its checksum/receipt, and the readable standalone `unpack-recovery.mjs` from the backup folder. Verify the archive checksum against the receipt. Install Node.js 24 from its official distribution if needed.
3. Run `node unpack-recovery.mjs <archive.enc> <NEW-empty-recovery-folder>`. Enter the Recovery Kit password at the hidden prompt. The script authenticates the AES-GCM archive, validates every file hash and refuses existing output directories/unsafe paths. It requires no repository or third-party Node modules.
4. Read `inventory.json` and coverage/restore receipts. The archive contains `repository.bundle`, the working-source snapshot, database dump, safe Auth identities and actual Auth schema metadata, role/membership inventory, and the exact registered evidence files. The encryption key and private runtime credentials are deliberately outside it.
5. Recover Git history with `git clone repository.bundle <new-repository-folder>`. The bundle represents committed history; apply the included `repository/` source snapshot if it contains newer work. Keep extracted evidence read-only. Run `npm ci` with the preserved lockfile.
6. Recreate ignored `.env.local` privately from Recovery Kit notes and `.env.example`. Download the project's public CA from Database Settings; retain `sslmode=verify-full`. Set `PADOVA_EVIDENCE_ROOT` to the extracted evidence directory. Never reset existing passwords merely to diagnose a connection.

Do not claim a full managed-service restore solely from a successful PostgreSQL restore.

1. Regain Supabase account ownership and inspect the existing US project. If the project is intact, first try verified-TLS restricted connection and `npm run db:check`; a laptop failure alone does not require a database restore.
2. If database recovery is necessary, compare the backup to the target and prepare an exact object/data restore plan. **Stop for explicit approval before overwriting or deleting anything.** Do not run `pg_restore --clean`, reset the project or create replacement projects automatically.

Only after **full recovery acceptance** may the Owner approve changing the existing operational/backup gate.

## Ongoing backup process

Run `npm run backup:system` using the dedicated backup credential. It opens a repeatable-read snapshot, captures the domain database and safe Auth/configuration metadata consistently, includes Git history/current source and verifies every registered evidence file's bytes/hash before encryption. Upload **only the encrypted archive and nonsecret recovery tools/receipts** into the dedicated private Drive folder; never upload the Recovery Kit CSV or keys there.

Verify remote size/checksum, download/decrypt/readback and periodically repeat isolated restoration. Retain dated archives; no automatic deletion is authorized. A scheduler, unattended Drive upload credential, failure notification and a verified Owner-controlled runner are required before calling the recurring process complete. An interactive connector upload is a checkpoint, not an unattended backup service. Record the last successful off-device backup and restore date, failures and remaining coverage gaps in BUILD_STATE.
