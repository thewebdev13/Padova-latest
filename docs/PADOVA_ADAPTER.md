## How the adapter preserves completed workflows

`src/lib/padova-storage.ts` maps the repository's known SQL relations to qualified `padova` compatibility views or native support tables. It lexes relation/qualifier positions without changing literals, comments or output aliases. This is a closed application-query contract, not a general-purpose SQL translator or a public arbitrary-SQL endpoint. The generated manifest, views and narrow INSTEAD OF triggers preserve current DTOs/forms.

- Parties, bookings, confirmations, itinerary, charges, supplier obligations, assets/movements, commissions/referrals, refunds, notes and audit use their existing canonical tables and IDs.
- Unified payment DTOs route incoming money to existing `receipts` and outgoing money to existing `supplier_payments`; customer/supplier allocations use their respective existing tables. Refund cash entries link the cash record to existing case settlements; they do not create another recognition or journal. Customer allocation reversals use existing negative linked receipt allocations.
- Existing `requests` remains the completed idempotency/result ledger. `command_context` adds payload/kind and journal linkage; results are not duplicated. Deferred guards require command completion, balanced journals and valid lot balances in the same transaction.
- Exact `numeric(18,2)` dollar storage remains intact. Checked SQL conversion exposes safe integer cents to the financial engine and divides cents exactly on writes. Whole points/quantities are separate from dollar basis; fractional or unsafe conversions fail rather than round silently.
- FIFO lots, multi-lot returns, transfers and acquisition/sale settlement links extend existing asset IDs and movements. Existing original face/basis values are preserved. An append-only traveler-status event table supports partial cancellation without altering immutable membership rows.
- Existing bookings not created/adopted through this adapter remain read-only to the new posting engine. Their unknown original economics stay NULL. No staged evidence or old balance is silently adopted or recomputed.
- The New York business timezone and original backup/write gate remain authoritative. The server role cannot unlock settings. Operational commands stay locked until both the existing flag and backup verification are satisfied. Notes/attention acknowledgments retain their limited nonfinancial behavior.
- Owners can see a read-only list/count of preserved source reviews in Needs Attention. It shows up to 100 open reviews; it does not resolve/import them. Employees do not receive these source-review titles/payloads.

## Supabase Auth integration

`src/lib/supabase-auth.ts` implements the documented Auth REST contract, pinned to this US project; no new SDK dependency is required. Password creation/verification/change is handled by Supabase Auth. The existing login, user-administration and recovery interface remains; `padova.staff.user_id` and actor foreign keys use actual Auth UUIDs. No password-hash column is added to the existing schema. User-editable JWT metadata never controls permissions.

The browser retains an opaque HttpOnly app cookie. Its hashed server session stores encrypted provider access/refresh state using AES-256-GCM with a separate private 32-byte key. Requests verify the provider user and current database active status/authorization version; expiry triggers refresh. Changed provider metadata timestamps, bans, deactivation, grant changes and app password changes invalidate applicable access. Provider tokens/keys/passwords never enter audit output.

Owner-controlled setup links and personal offline codes preserve the working recovery UX. Their proofs are hashed, single-use and expiring where appropriate; successful recovery changes the password in Supabase Auth. Recovery claims and local session revocation commit **before** the external provider change, preventing replay after a provider failure. A failed attempt consumes its proof; unused personal codes remain available. Failure/success events are audited. No automatic recovery/invitation email is sent by this implementation; delivery remains through an Owner-verified private channel.

The first Owner is created only from the authorized private terminal after schema/configuration acceptance. Its supplied email is marked verified by that administrative enrollment; verify the actual individual's email before running it. Subsequent people are created through Users & Permissions with no usable shared/default password and need their own setup proof. Additional employees need rows/grants, not schema redesign.

Provider administration and PostgreSQL cannot share an atomic transaction. A provider account created just before a database failure may remain without Padova membership; it has no application access and must be reconciled by the Owner, not automatically deleted. Email-update failure can likewise require profile reconciliation. Real provider/network/configuration acceptance is still required before live use.
