# Enter each fact once — 31 October 2026

The Owner's booking-entry simplification instructions supersede the earlier product freeze and readiness verdict. Historical reconciliation, import and cutover are paused. This correction uses the same checkout, branch, existing schemas, ledgers and individual sessions. No migration, production financial posting, original-source edit, mapping change or gate change is part of this pass.

## Entry design

The preserved accounting headers were read solely as UX reference: customer, passengers, route, dates, confirmations, cost, sale and payment facts occupied a short row. The application now asks those facts once and creates its existing connected records underneath. Normal products and filters offer Flight, Hotel, Car and Other. Older combined/legacy records remain readable under All; no historical records or catalog evidence were deleted.

- Names are selected directly in their picker. A new traveler takes a name and one Create click; no email, contact or profile dialog. The input regains focus for the next passenger. Existing likely names stay visible, separate-person creation is explicit, failed lookups cannot silently bypass duplicate checks, and retry keys prevent duplicate creation on a retry. Customers, providers and sellers also have name-based inline creation; companies can be created directly. Travelers never become customers automatically.
- Airline/property/rental company identifies the travel provider. Booking channel, outside seller and payment owner stay independent. Provider results remain role eligible. No normal Actual Supplier selection, and no rental-provider list for Other. Required account/card ownership and financial permissions remain enforced on the server.
- Structured travel generates the reservation summary. One Way asks departure only; Round Trip asks departure/return; Multi-City asks segment dates and derives its range and flight numbers. Hotel uses check-in/out, Car pickup/drop-off, Other start/optional end. Optional Car times inherit their dates. Other's description remains a separate structured fact. Revisions update generated summaries and a single generated booking title, retain custom summaries, clear obsolete effective segments and preserve original rows/versions.
- Ordinary entry starts with the seller/cost path. Special points, vouchers, certificates, owned value and extra payments appear when chosen. Award points inherit the selected program. Quantity × agreed rate replaces manual point-cost entry. Repeated program/quantity/unit controls were removed from advanced component details. Original inventory basis and seller settlement still use the existing commands.
- Customer/seller actual payment amounts derive status and balance. Full-payment shortcuts fill the known amount; there is no second payment-status question. Blank cost stays Unknown; untouched default cost controls create no financial event. Direct customer-card ownership defaults to the selected customer, with an optional override limited to linked people. Optional card metadata, receipt details, taxes and exceptions stay collapsed.
- Comparable price is visible for percentage pricing or a voluntary comparison. Capital One requests inherit the immutable original booking amount and receiving profile. Entering the lower price calculates requested/expected credit. Exceptional original-rate overrides require a reason. Approval/expectation remains separate from an actual receipt, amount, date and reference; receipt creates reusable value exactly once.

## Verification and boundaries

Existing accounting tests cover obligations versus settlements, acquisitions versus original-basis use, direct customer spend, expected versus received credits/commissions, unknown amounts, retries, audit history and independent permissions. Added regressions cover original-rate/profile inheritance, explained overrides, receipt replay, generated metadata preservation and itinerary/type changes with unchanged journal counts and immutable original travel. Current final run results and preview status are recorded in BUILD_STATE.

Private fresh source capture and the independent 109-table US restore completed before the Owner stopped reconciliation remain preserved. None has been adopted as live financial data. Existing historical mappings, Owner decisions and migration evidence remain unchanged. Prepared US extensions remain uninstalled; this is a verified product correction in Practice/QA, not authorization for production historical adoption.
